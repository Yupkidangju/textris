# 테마 고도화와 향후 2보드 화면의 확장 설계

작성: 2026-10-14, Asia/Seoul. 근거: 사용자 테마 점검 요청과 후속 2인 배틀 대비 요청,
`spec.md`, `designs.md`, AI 구현 문서 표준,
`audit/theme_enhancement_review_20261014.md`.

## 범위와 상태

현재 제품은 1보드 싱글플레이다. 이번 문서는 테마 고도화 과정에서 나중에 2개의 보드를
같은 화면에 배치할 수 있도록 준비하는 **예정 설계**다. 배틀/AI/온라인 기능의 구현 완료를
뜻하지 않는다. AI 전략·공격량/방어 규칙·네트워크 동기화·배틀 저장 방식은 이후 별도 기능 명세 대상이다.
현재 화면과 저장·테마ID·음악·리플레이 계약은 그대로 유지한다.

## 공통 화면 구조

```text
                  공용 테마의 천장 / 원경 / 타이틀
┌───────────────────────────────────────────────────────────────┐
│       P1 / YOU          모드·시간·대전 상태       P2 / AI·상대  │
│                                                               │
│  HOLD·NEXT  ┌──────────┐   중앙 정보 영역   ┌──────────┐ HOLD·NEXT│
│  점수·상태  │ P1 10×20 │      VS / 예정     │ P2 10×20 │ 점수·상태│
│            │          │    공격/대기 정보   │          │          │
│  P1 연출 ← │          │                  │          │ → P2 연출 │
│            └──────────┘                  └──────────┘          │
│        P1 성취·위험             P2 성취·위험                    │
│             공용 테마의 바닥 / 원근 / 복귀·조작 안내             │
└───────────────────────────────────────────────────────────────┘
```

- 경기의 공용 테마 1개가 화면 전체의 미술 언어를 만든다. 현재 6개 테마를 유지한다.
- P1/P2는 같은 보드 크기와 가독성을 갖는다. P1은 왼쪽, 상대는 오른쪽이다.
  YOU/AI/PLAYER 등 상대 종류가 달라져도 화면 구조는 같다.
- 플레이어를 P1/P2 텍스트·위치로 구별하고 색상 강조는 보조로 사용한다.
- 공용 원경과바닥, 플레이어별 중경·국소 효과, 두 보드/HUD, 중앙 정보, 공용 모달의
  순서로 합성한다. 보드와정보는 불투명/보호된 영역이다.
- 중앙 정보 영역은 향후대전 데이터가 제공될 때만 표시한다. 현재화면에 빈배틀 메뉴나
  공격 수치·온라인 접속 UI를 노출하지 않는다.

## 창 크기별 예정 구도

각 보드의게임 셀은10×20, 셀당2문자이고 바깥 프레임은22열×22행이다.
터미널 마지막 열은 현재와같이 사용하지 않는다. 좌표는0부터 시작한다.

| 크기 기준 | 구도 | 예시 보드 원점 | 보드 주변 정보 |
| --- | --- | --- | --- |
| 64×28 | 2보드 압축형 | P1(5,3), P2(36,3) | 각상단 HOLD·NEXT5를문자 토큰으로 표시, 하단 핵심수치, 중앙9열 상태, 외곽5열 테마 문양 |
| 80×30 | 2보드 기본형 | P1(10,4), P2(47,4) | 외곽여백 확대, 핵심 정보/축약 미리보기, 중앙15열 상태와효과 통로 |
| 120×40 | 2보드 확장형 | P1(18,10), P2(79,10) | 양외곽 HOLD·NEXT·통계, 중앙대전정보, 상단 테마상징·큰성취, 하단공용바닥 |
| 160×50 이상 | 같은2보드+확장장식 | 사용가능 폭·높이에서재배치 | 보드셀 크기는유지, 테마거리층·환경효과·중앙정보를확장 |

64×28 압축형의 행 배치 예시:

```text
0       경기 제목 / 상태 / 시간
1       P1 이름                         P2 이름
2       HOLD + NEXT5 토큰                HOLD + NEXT5 토큰
3..24   [22×22 보드]     중앙 상태       [22×22 보드]
25      P1 핵심 수치                     P2 핵심 수치
26..27  조작 / 상태 안내
```

중앙상태와 외곽 장식은 보드 사이/바깥에서만 표현한다. 작은 창의NEXT는5개를 유지하되
도형 대신 I/O/T/S/Z/J/L 토큰으로 축약한다. 실제배틀 개발 시 이름·점수의최대길이와
중앙정보 표시우선순위를정하고 초과 문자열을 안전하게축약한다.
최소지원크기와 온라인중축소/도움말/정지 정책은 실제배틀 모드 명세에서 최종 확정한다.
위의64×28은 **공간적으로 가능한 예정구도**이며 실제키 입력·폰트·가독성 검증 완료가 아니다.

## 나중에 구현할 렌더링 계약

다음은 예정 인터페이스이며 현재 코드의 공개 API가 아니다.

- `BoardViewport`: `player_id`, `board_rect`, `hud_rects`, `effect_regions`.
  보드 원점·정보보호영역·연출가능영역은각레이아웃에서계산한다.
- `PlayerView`: 읽기전용 보드/활성블록/고스트/HOLD/NEXT/표시통계/상태.
  같은그리기컴포넌트를1보드 또는2보드목록으로사용한다.
- `VisualEvent`: `player_id`, `kind`, `start/end`, `power`, 보드상대좌표의`cells/rows`.
  삭제행·착지위치를해당플레이어의원점에서화면좌표로변환한다.
- `MatchView`: 현재모드·전체상태·공용시간과추후제공되는대전표시정보.
  테마가직접게임엔진·AI·네트워크를조회하지않는다.
- `ThemeScene`은화면중앙1개보드좌표에고정하지않고viewport목록과읽기전용시각상태를받는다.
  보호마스크는각보드/HUD의합집합, 공용배경은한번만그린다.
- P1/P2의삭제·위험·회복·피버는구분한다. 자신의흔들림/섬광이상대보드좌표나HUD를움직이지않는다.
  향후공격효과는원점/대상ID를받아허용된여백에서표현한다.
- 효과·잔상·입자·캐시는화면전체예산을공유하며2보드라고무조건두배로늘리지않는다.
  공용음악은1곡이고두보드의표시는게임난수·점수·저장·온라인진행을변경하지않는다.

## 테마 고도화에 먼저 반영할 기준

1. 보드/HUD/여백 구도를렌더링로직과분리하고현재1보드에도viewport기준을사용하도록설계한다.
2. 국소효과의좌표·의미·수명과배경의상태반응을플레이어별로분리한다.
3. 테마별세부표현은공유환경과각플레이어영역을구별해제작한다.
4. 작은창에서테마식별성, 두보드/HUD보호, 동시성취의우선순위와전체성능예산을검사한다.
5. 실제배틀 구현단계에서AI/온라인 규칙을명세하고2보드입력·진행·연결상태를재검증한다.

현재 싱글플레이를 확장하는 설계 준비이며, 이번 작업에서 배틀 관련 코드·메뉴·저장 필드는 추가하지 않았다.

## 승인 후 현재 구현 상태 (2026-10-14)

구현된 경계는 `art.BoardViewport`, `Layout.viewports`, `battle_viewports`,
`RenderContext.viewports/clip_rect`, `visual_state.VisualState`, `Cue.player_id/variant`다.
ThemeScene은 viewport별 사건/상태를 격리하고 UI의현재보드는 game_layout 원점을사용한다.
PlayerView/MatchView와실제2게임제어·진행·네트워크는예정계약으로남아있다.
